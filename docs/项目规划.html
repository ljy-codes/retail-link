长期工程 · 推进原则

问题服务主线，不让细节拖慢进度

持续遵守

零售通是长期大工程。每日疑问和问题处理以当前阶段目标为中心，先保证主线持续产生可验证结果，再集中处理低优先级细节。

GitHub长期使用main、macos、windows三分支。共享功能在main维护，Mac带头验证，Windows按同一基线跟随。规则见GitHub分支与版本规定；本轮仅同步本机工作区，不提交、推送、打标签或发布。Windows分支不代表已完成安装包。

原则执行方式
控制问题数量每份日期答疑最多保留 5 项，优先记录影响多个功能、阻塞验证或可能造成错误决策的问题。
问题分级高优先级立即处理；低优先级先记录到答疑文档，不打断当前开发和验证主线。
允许继续验证可以用透明默认值、可配置规则和可撤销操作推进的，不等待所有业务口径完全确定。
阶段时间盒每个阶段设置目标、验收条件和时间盒；达到条件就进入下一阶段，遗留小问题集中处理。
01 · 长期目标

一个可以逐步接入更多工具的运营操控台

方向已确定

暂定名称为 零售通。先把库存、销量和每日经营数据转成可靠结果，再逐步接入更多高频运营场景。新增功能应建立在真实使用和已确认规则上。

01

结果可以直接使用

在网页中查看经营指标、商品明细和数据问题；Excel 是输入来源之一，日常查看不依赖打开 Excel。

02

自动处理，允许补正

常规读取、识别和计算由工具完成；识别不足或业务调整时可手动配置，保留修改来源和还原方式。

03

让规则适应业务

工作表、字段映射、统计口径和目标阈值可配置；数据连接方式逐阶段扩展，避免把样例格式固化成唯一模板。

数据类型目标流程与具体实现当前状态

输入适配 · 用户新增目标

文件格式会变化，人工调配后可以继续复用

已实现 · 持续适配

同类库存、销售或经营文件的表名、表头行、列顺序和布局可能改变。工具先自动识别；识别不足时，用户直接在页面调整对应关系并保存为配置，下次遇到相同格式可以复用。

步骤具体实现与约束
自动判断检查工作表、候选表头与业务字段，识别横向日期表或逐行日期表。未识别角色、缺少日期或商品列时明确提示，不强行生成完整结果。
页面调配可重新指定数据角色、工作表、表头行和字段列。原始预览与来源位置帮助用户核对；按配置重新分析，而不要求先去 Excel 改成固定模板。
保存复用保存格式映射与规则参数，形成命名配置。用于新文件前检查实际工作表和列，失效映射需重新指定。当前商品的人工金额／数量修正不跟随格式配置套用。
边界处理当前支持常见宽表和长表；任意多层交叉表、多个表拼在同一工作表或复杂自定义公式，不承诺自动理解。后续根据真实原始文件逐项增加适配能力。
格式适配解决“从哪里读取”，业务口径解决“如何计算”。两者分别配置并随分析快照保存，避免格式变化时悄然改变指标含义。
持久化 · 用户新增目标

每次结果形成快照，历史可翻看、删除也可恢复

已实现

历史记录应在重启后继续存在。打开历史时优先呈现当次保存的结果，保留当时的配置、人工修正、数据问题和来源；不使用今天的规则静默重算过去的结果。

完整、不可变的结果快照

  • 每次分析保存独立 ID、生成时间、版本、文件标识、统计期间、完整指标与商品明细。
  • 配置、映射、手工调整、问题说明和来源信息一起保存。后续修改配置或源文件，不改写已保存快照。
  • 历史列表支持分页与数量统计；取消自动只保留 30 条的清理逻辑，旧记录不会因新增分析自动丢失。
  • 快照查看不依赖当前文件会话。需要打开原始数据时，按保存的来源标识定位文件；找不到或内容已变更时明确提示。

可恢复的删除

  • 普通删除将历史 JSON 从 本地数据/history/ 移到 本地数据/history_deleted/；用户可在回收站翻看和恢复。
  • 恢复后回到正常历史列表；相同 ID 已存在时拒绝覆盖，保留现有记录。
  • 删除历史只影响分析记录，不删除原始 Excel。当前不提供永久清除或自动淘汰旧记录。
  • 采用原子写入与并发锁，完整写好再发布；新记录不能覆盖旧快照，损坏记录也不应被悄然忽略。
持久化、历史详情、来源定位、软删除与恢复已接入服务和页面。10项历史模块测试和15项接口测试通过，浏览器已验证删除、恢复、打开快照；正式业务口径仍需按沟通清单确认。
04 · 具体实现

本机服务负责解析，网页负责查看与配置

当前架构
原始资料用户原件、目录选取文件、上传归档
网页交互导入、看盘、配置、Excel 保存、恢复和数据迁移
文件读取与分析请求 ↓　↑ 结构化结果与来源
Python 本地 HTTP 服务仅监听 127.0.0.1；文件会话、目录扫描、格式检查与分析记录
按映射读取 → 统一商品与单位 → 按日期筛选 → 计算与校验
openpyxl 分析引擎只读解析工作簿；独立计算指标；返回缺失、异常与来源

数据与映射规则

  • 按角色连接月计划、商品规格、编码对照、库存、销量、出库、报单、在途和货损；工作表名称与列字母可以调整。
  • 商品以稳定标识关联；编码按标识符保留，简称与编码冲突明确提示，不凭不同表的相同行号关联商品。
  • 保留大单位、箱规及小单位的区别；数量比较须采用一致单位，金额须采用匹配的单价。
  • 辅助汇总区按商品键关联；日期明细按统计月份和截止日期筛选，源整月金额不得直接替代不匹配的部分期间。

计算与保存规则

  • 已确认采用报单金额、单商品85%考核及数量×单价重算。当前已按单品独立计算并合计正差额；净销量和货损双轨另行落实。
  • 无数据与真实 0 分开。零分母、缺失单价或观察天数不足时显示未计算；合计比例采用匹配范围的分子、分母计算。
  • 年份不自动改写；开启年份对齐必须由用户主动选择，并保留提示。库存池未确认时不输出可售天数。
  • 在途独立展示；超期只标记待确认，不直接删除或认定到货。未来日期不计入当期实际。
  • 人工调整与源数据分开、可还原；复用配置不携带上个文件的商品人工调整。当前版本原始工作簿只读、不执行宏；已确认后续允许设置开启受控写回，每次预览确认，尚未实现。
当前依赖 Python 3.10+ 与 openpyxl 3.1.5，前端使用原生 HTML／CSS／JavaScript。首版不依赖前端构建工具；分析快照采用本地 JSON，日记录采用 SQLite；未引入云端账户或外部采集服务。
每日经营数据 · v0.1.9增强

按日记录每款售价，关联同一天的销量

已实现 · 已验证

用户每天维护一份价格表，次日另存后更新售价。平台应把这些文件转成可持续累积的日记录，而不是只保留最新价格。价格表格式变化时，沿用自动识别与人工映射入口。

能力具体实现与边界
按日保存以日期、商品及适用店铺／仓库作为关联键，分别保存当日售价和销量、来源及导入时间。11月21日的新价不能覆盖11月20日记录。
变动格式适配识别常见长表、单日快照及双层日期价量横表；日期表头、销量／售价表头和列可调，错列或跨日期组会明确提示。合并仓位可继承，完整年份不猜测；无日期快照仍须指定业务日期。
日期准确对应只把同一天的价格与销量配对；今日售价不能直接用于昨日销量。缺少某日价格或销量时保留空缺，不擅自沿用最新价格。若一天多次变价，后续可细化时段或成交明细。
历史与去重同日期、商品与仓位唯一；逐项预览名称、售价及销量的旧新差异，默认跳过重复；只把旧空到新有标为补齐，旧有变空列冲突。映射、策略或旧值变化后须重新预览；显式更新保留旧版，支持软删除与恢复。
商品对照与导出商品ID、规格与仓位可从订货表预览导入和手动维护，不按名称自动合并。Excel/CSV按筛选范围导出全部匹配日记录；Excel同时附范围口径和当前商品对照，历史仍使用保存时的标识与数值。
金额含义日记录的售价可能是标价，售价乘销量只可称为估算金额；实际成交额仍应来自平台成交数据，不据此推算真实利润。
先建立“导入／补录 → 日期与商品匹配 → 保存日记录 → 翻看价格和销量”的闭环。涨价后销量变化可用于观察，不直接宣称价格造成销量变化。
