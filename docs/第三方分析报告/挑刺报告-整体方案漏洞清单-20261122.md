## 0. 先说结论

**底子不差，但现在的“整体方案”不是一个能交付的零售通，而是一个“Excel 解析看盘器 + 日价格台账 + 一套很讲究的外观”。**

三个“看起来”和三个“实际上”：

| 看起来 | 实际上 |
| --- | --- |
| 零售通，库存、销量、计划、货损一站式看盘 | 只解决了“把整理过的 Excel 读出来看”，没有解决“今天该报多少、该卖多少、该不该补货、活动亏不亏” |
| 65 项自测通过，浏览器已验证，v0.1.1 已交付 | 65 项是自己出题自己打分；真实仓库原表 0 份、平台原始导出 0 份、人工并行对账 0 次、客户签字 0 个 |
| 格式自适应、主动发现问题、无需打开 Excel | 表头变了主要靠人工映射；问题主要靠“金额差 0.02”提醒；`.xls` 要先另存、公式不重算、CSV 导出还会被 Excel 改格式 |

一句话：**能演示，不能交付；能看数，不能决策；能自测，不能验收。**

### 两条边界先对齐（按用户更正）

- **本地文件：需要具体读写。** 对原始工作簿默认只读是保护策略，不是能力缺失；生成/导出、以及经用户确认后写回本地文件，属于工具能力范围。评审要挑的是“读写是否可控、可追溯、可回滚”，不能把“没有写能力”当成默认前提。
- **线上数据：只读，不写回平台。** “不能自动改价、上架、发货、写回后台”是明确边界，不是漏洞。要审的是读取侧的认证、频率、失败恢复、平台合规与数据最小化。
- **电脑故障、云同步、网盘备份：用户自己的运维责任。** 不计入本工具缺陷；工具内只需要保证本地数据能整体导出/迁移、格式可读，不承诺电脑级容灾。下文涉及“备份”的条目按这个边界收窄。

### 先给三句公道话

不是全盘否定。下面这些做得对，应该保留：

- 对原始工作簿默认只读、不改写、不执行宏；本地文件整体支持读取与生成/写出，线上数据只读不写回；
- “缺失”和“真实 0”分开，源金额和明细重算分开；
- 历史快照采用完整 JSON、原子写入、软删除与恢复；
- 服务只监听 `127.0.0.1`，POST 有 Origin 白名单；
- 没有为了“自动化”去伪造数据，未知就留空。

但这些都是**工程卫生**，不是**业务价值**。工程卫生做到 80 分，业务口径 0 分，客户还是不会买单。

## 1. 最致命的洞（P0）

### 1.1 业务口径没冻结，指标就是“数字对数字，单位靠缘分”

`概览/答疑文档/零售通-20261121.xlsx` 里五个核心问题——计划口径、原始样表、库存归属、折价定义、金额取值——**解答列全是空的**。但代码里已经默认了一整套：

- `planBasis = orders_amount`：默认按报单金额考核；
- `targetRate = .85`：默认 85% 门槛；
- `amountMode = source`：默认优先源表金额；
- `alignSalesYear = false`：默认不跨年对齐；
- `inventoryComparable = false`：默认不计算可售天数。

这不是“敏捷”，这是**先斩后奏**。客户一句“计划量是件数不是金额”，达成率立刻从 92% 变成 0.03%，或者从 37% 变成 3700%。

更具体：`plan` 字段没有单位校验，`planBasis` 却可以在“报单金额/出库金额/报单数量/出库数量/销售数量”之间切换。用户把“计划 1000 件”的表切到“报单金额”口径，工具不会拦，只会认真算出一个毫无意义的比率。

**客户会怎么骂：**“你这达成率是算出来的，还是猜出来的？”

### 1.2 库存池没确认，可售天数默认是空的；一旦打开，又不是交接文档里的公式

- 默认 `inventoryComparable = false`，所以“现货可售天数”这个招牌指标在正式看盘里是 `—`。
- 如果用户勾选“同一库存池”，代码算的是 `stockSmall / averageSales`，**不含在途、不含安全库存、不扣预计到货**。交接文档的公式是：

  `可售天数 =（当前可用库存 + 预计到货库存 - 安全库存）÷ 日销售目标`

  两个东西同名不同义。
- `transitDays` 同时被当成“在途超期天数”和“低库存预警阈值”，两个业务概念用同一个参数，客户改一个，另一个跟着变。
- 库存只有当前快照，没有每日库存历史。客户问“上周三库存多少、这周降了多少”，答不了。

**客户会怎么骂：**“南京仓 3000 件、南京多多可售 1800 件，你按哪个算？算出来 12 天，我信谁？”

### 1.3 货损不是核算，是“手填多少就是多少”

工作流程写得很清楚：货损来自“新出库 + 昨日结余 + 账面库存与实盘库存差异”。当前实现只做了两件事：

- 从货损表读一个 `lossAmount` / `lossQuantity`；
- 用 `lossAmount / outboundAmount` 算货损率。

没有期初、入库、出库、实盘的恒等式核对，没有“货损数量 = 应存 - 实存”的重建，也没有把“数量 × 单价”与手填金额的差异变成待确认项。样例里商品 B 货损 2 个、单价 7.7、金额填 77，工具只能提示“不一致”，不能告诉客户“真实货损应该是 15.4 还是 77，依据是什么”。

**客户会怎么骂：**“你这不是货损核算，是把我的错数抄了一遍，还给它配了个百分比。”

### 1.4 销量口径没定义，退款/退货/仅退款全部缺席

“销售明细从多多后台导出”只是数据来源，不是业务口径。当前 `sales` 角色没有退款、退货、仅退款、发货、成交、订单状态等字段，工具默认把导出的数量当“销量”：

- 拼多多“仅退款”比例不低，销量虚高会直接推高日均销量、压低可售天数；
- 用虚高销量做“7 日均销量”，再用它算补货和活动，越算越乐观；
- 没有“成交额”概念，售价 × 销量只能叫估算，不能叫收入。

**客户会怎么骂：**“后台成交 800 单，退款 120 单，你按 800 算日均，让我备货，压货你赔？”

### 1.5 85% 是品牌返利门槛，但返利本身没算

计划量之所以重要，是因为“关系到品牌费用返还，最低达成 85%”。当前只显示“距目标差额”和“剩余每日需完成”，没有：

- 返利阶梯（85%、100%、110% 分别返多少）；
- 未达标的扣罚/损失；
- 冲量带来的折价、活动费、货损，是否吃掉返利；
- 按单品、品牌还是整体考核。

**客户会怎么骂：**“你告诉我还差 3 万，但没告诉我冲这 3 万要亏 5 万，这表是帮我还是坑我？”

### 1.6 只有“看盘”，没有“操盘”：每日最低销量、报单建议、补货、活动风险全缺

交接文档的第一优先级是：库存导入、可售天数、**每日最低销量**、价格/活动风险、每日运营任务。当前交付的是“昨天怎么样”：

- 没有“今日最低销量 = max(基础销售计划, 需消化库存 ÷ 剩余天数)”；
- 没有“今日建议报单量”，没有箱规、起订量、在途、安全库存、供应商交期约束；
- 没有补货点、补货量、下单时间；
- 没有“活动价低于成本/低于总部限价/活动后亏损”的检查；
- 没有每日任务清单，不能派给仓库/采购。

**客户会怎么骂：**“我看完这张表，然后呢？还不是回去开 Excel 自己算。”

### 1.7 多仓、多店铺、多文件、多平台：现在只认一张表

- `_sheet_match` 每个角色只选一张工作表；样例里明明有“南京出库、芜湖出库、徐州出库”，工具只会命中一张，其他表**不提示、不汇总、不报警**。
- 多仓库存表、多店铺销售表同理，只取第一张匹配的。
- 每日价格/销量是单独导入的，但主分析引擎**完全不读** `daily.sqlite3`；日价格模块和看盘是两张皮。
- 平台每天一个导出文件，主分析要求一个工作簿里齐活；没有多文件合并，客户还是得先在 Excel 里拼表。

**客户会怎么骂：**“我有三个仓、两个店、一天一个导出，你让我先手工合并？那我要你干嘛？”

### 1.8 数据地基五件事：主键、单位、去重、零值、日期，全都有洞

| 地基 | 现状 | 后果 |
| --- | --- | --- |
| 主键 | 用“商品简称”字符串当 `meta` 的 key，`code` 只是展示字段 | 改个简称，历史断；两个商品同简称，直接合并；所谓“稳定标识关联”并未实现 |
| 单位 | `pack` 只对报单/在途生效；销售、出库、货损默认小单位 | 仓库按箱出库时，数量、金额、货损率全错；日价格记录也没有单位字段 |
| 去重 | 明细行没有唯一键，同商品同日多行直接相加 | 复制粘贴两行，销量翻倍；两个仓同商品同日，被合并成一个数 |
| 零值 | 销量空白=缺失；日均要求 7 天全有 | 真实零销量被当成“没数据”，7 日均销量和可售天数永远算不出 |
| 日期 | 宽表日期靠表头解析；合并单元格、多级表头、无年份表头支持弱 | 仓库常见的“商品列合并”“11.20 表头”会漏行或错年；`asOf` 自动取不到时回退到今天 |

**客户会怎么骂：**“你这不叫数据治理，叫数据看命。”

## 2. 会算错 / 算不出 / 算不全的具体漏洞

### 2.1 商品主键用“简称”，不是稳定 ID

`analyzer.py` 里 `meta` 以 `_text(product)` 为 key。`code` 只用于展示和冲突提示，不用于关联。结果是：

- “可乐”改名“可乐330”，历史两套商品；
- 两个不同编码都叫“可乐”，被合成一个；
- 同一商品换链接，平台 ID 冲突只 warning，不阻断；
- 18–19 位平台 ID 若以数字存储，float 精度只有 15–16 位，可能悄悄改号。

**正确做法：**平台 goods_id / SKU ID + 内部商品编码 + 规格，三者建映射表；简称只做显示。

### 2.2 多仓/多表只取一张，且不告诉用户“还有表没读”

`_sheet_match` 先精确匹配，再子串匹配，返回第一个。样例的“南京出库/芜湖出库/徐州出库”不会全部进入分析。文档说“13 个工作表、10 款商品”，但实际只把其中一张出库表当数据源。客户以为全量，实际是抽样。

### 2.3 明细不去重，也不做“明细合计 vs 源表合计”的对账

- 同一商品同一天出现两行（两个仓、两批、复制粘贴），`grouped[pid]` 直接累加；
- 没有 `(date, product, shop, source)` 唯一性检查；
- 没有“表内合计 = 明细合计”“出库 + 期初 - 期末 = 销售 + 货损”的恒等式；
- 所谓“主动发现问题”主要查行内金额 vs 数量×单价，查不到业务级重复。

### 2.4 零销量=缺失，日均销量和可售天数被“真实零”卡死

`averageSales` 要求 `cutoff` 前 `averageDays` 天**每一天**都在 `sales["daily"]` 里。宽表空白单元格不会生成事件，长表没有行也不会生成事件。于是：

- 昨天真没卖，单元格空着 → 昨日销量 `—`、7 日均销量 `—`、可售天数 `—`；
- 用户只能去 Excel 把每个空白改成 0，再导回来；
- 这和“无需打开 Excel”直接冲突。

### 2.5 单位混用：报单按箱、出库按件、销售按小单位，没有字段区分

- 报单/在途：`quantity * pack` 转小单位；
- 销售/出库/货损：`pack = 1`，默认就是小单位；
- 库存：有大单位/小单位两列，可换算；
- 日价格记录：只有 `price` 和 `salesQuantity`，没有“每箱/每件/每小单位”。

仓库实际按整件盘点、按箱出库很常见。只要出库表是“箱”，`outboundAmount`、`supplyAmount`、`lossRate`、`coverageDays` 全部失真。

### 2.6 合并单元格、多级表头、无年份日期：中国式 Excel 的重灾区

- 商品列合并：openpyxl 只有左上角单元格有值，下面行 `product` 为空，直接跳过 → 漏数据；
- 多级表头/两行表头：`_header_row` 只按前 15 行打分，容易选错；
- 无年份表头“11.20”：分析时按当前统计年份硬套，历史文件会错年；自动 `asOf` 在 `inspect_workbook` 里又识别不到，回退到今天；
- 周表头“11.20-11.26”：`_date` 解析不了；
- 合并的标题行、说明行、合计行：靠 `_total_label` 过滤，覆盖不全。

### 2.7 文本数量“10箱 / 1,000件 / 两箱”直接判无效

`_number` 只处理数字、逗号、￥/¥。仓库手写登记里“10箱”“5件”“约3箱”很常见，工具报 `INVALID_QUANTITY`，行被丢弃。客户得回去把字改成数字，再导一遍。

### 2.8 重复计划行会双倍计入计划

`summary` 里同一商品出现两行时，虽然会报 `DUPLICATE_PRODUCT`，但后面仍然执行：

```python
item["plan"] = (item.get("plan") or 0) + val
```

也就是说：**提示归提示，计划照加。** 合计计划被放大，达成率被压低，客户看到“差很多”可能只是表里重复了一行。

### 2.9 公式缓存 / 外部链接：所谓“不用打开 Excel”是假的

`openpyxl` 用 `data_only=True` 读的是**缓存值**：

- 文件由 WPS/其他系统生成、没有缓存 → 全是 `None`；
- Excel 改了公式没保存/没重算 → 读到旧值；
- 外部链接没更新 → 静默旧数；
- 工具不会重算公式，也不会提示“这个公式没有缓存值”。

客户把“刚改完还没保存”的表拖进来，看到的可能是上周的数，还会以为工具算错了。

### 2.10 编码/长 ID/CSV 导出：可追溯性在最后一步断掉

- 数字型编码前导零在 Excel 里已经丢了，工具 `_text` 救不回来；
- 18 位平台 ID 以 float 存储会精度损失；
- 导出 CSV 后，Excel 打开时 `00123` 可能变 `123`，长 ID 可能变科学计数法；
- CSV 没有多 sheet、没有格式、没有公式，财务拿到还得二次整理。

### 2.11 负数、异常值、金额模式混用

- `_number` 接受负数；销售/出库/货损出现负数不会报错，比率可能变负；
- 没有“货损 > 出库”“供价 > 到岸价”“库存为负”“销量突增 10 倍”等业务异常规则；
- 金额模式是“每个商品各自决定”：有的用源金额，有的用重算，最后 `summary` 直接相加；只检查 `None`，不检查“口径混用”。

### 2.12 辅助汇总区识别很“样例定制”

只认 `产品/商品/简称/产品简称` 这几个表头；如果辅助区写“商品简称”，识别不到，就可能把主表金额当汇总金额。多条商品明细时，辅助汇总金额无法逐行分配，代码选择“按明细数量和价格重算”，但不会告诉客户“你表里的汇总金额被忽略了”。样例能过，真实表未必。

### 2.13 日均窗口、剩余天数、每日所需：算术上也有毛刺

- `remaining = max(0, (month_end - cutoff).days)`：截止日当天不算，11 月 21 日到 11 月 30 日是 9 天，不是 10 天；
- 剩余天数按自然日，不扣周末/节假日/仓库不发货日；
- 月底最后一天 `remaining=0`，`dailyRequired` 直接 `None` 或 0；
- `averageDays` 可以设 365，但销量表只有当月，必然“数据不足”，没有前置校验。

### 2.14 库存快照没有日期，历史复盘做不了

`STOCK_SNAPSHOT_DATE` 自己也承认：“库存表没有统一日期筛选；截止日期用于业务明细，不能自动还原历史盘点库存。” 这意味着：

- 选 11 月 1 日截止，库存还是今天的库存；
- 历史快照里的库存是“当时导入的那份表”，不是“当时日期的库存”；
- 客户问“上周三的可售天数”，答不了。

## 3. 产品与场景：有“看盘”，没“操盘”

1. **每日价格/销量模块是孤岛。** 记录得很认真，但主看盘不读它；不能把价格变化和销量变化放一起看，不能做“涨价后销量掉了多少”的分析，也不能用日销量替代 Excel 里的销量。记录完还得回去看 Excel。
2. **只导出 CSV，不导出 Excel。** 大陆电商的交付物默认是 Excel：多 sheet、格式、公式、合并单元格、打印。CSV 对财务/老板不友好，还会毁编码和长 ID。
3. **没有多文件合并、目录监听、URL 接入。** 文档写了“后续”，但客户当下的日常就是一天一个文件；不解决，工具只能当“周末复盘器”。
4. **没有告警、定时、移动端。** 库存不足只在页面里；老板/运营不会每天主动打开；仓库用手机；没有微信/钉钉/邮件，没有早报。
5. **问题清单没有闭环。** 每次分析生成新的 `issue-1`、`issue-2`，没有“待处理/已确认/已修正/忽略（附理由）”，没有负责人、没有备注、没有跨次追踪。问题越多，客户越不看。
6. **没有对比和归因。** 只有当期趋势；没有环比、同比、计划 vs 实际按日、活动日历叠加、价格带对比、竞品对比。无法回答“为什么这周掉了”。
7. **利润、营销费用、平台扣费、活动费、返利、退货、批次、效期全缺。** 这些不是“后续增强”，是电商经营表的基本盘。没有它们，“零售通”三个字撑不住。
8. **没有 SKU/链接/规格/组合装。** 一个商品多链接、多规格、多口味、多组合，全被“简称”压成一行；活动价和库存都没法按 SKU 管。
9. **没有多平台。** 样例是多多后台，名称叫“零售通”，但没有平台维度；以后接抖音/淘宝/京东，数据模型要重做。
10. **没有打印/分享/只读链接。** 老板要截图、要 PDF、要发群里；现在只能截屏。
11. **本地文件只完成了“读”和“浏览器下载”，没有“可控写回”。** 用户要求本地文件需要具体读写；当前 `/api/open` 只读，导出走浏览器下载，直接写回源文件的确认流程未实现。至少要有：选择目标路径、写前预览、版本/回滚、失败原子性，否则“本地读写”只兑现了一半。

## 4. 技术与安全：单人自用能跑，客户环境会翻车

### 4.1 没有登录、没有会话、没有审计

服务只监听 `127.0.0.1`，POST 做了 Origin 白名单，这比裸奔好。但：

- 同一台 Mac 上的其他进程/浏览器扩展/远程桌面用户，可以调用 `/api/open`、`/api/directory`、`/api/analyze`；
- `/api/open` 和 `/api/directory` 接受任意本地路径，能枚举、读取任意 `.xlsx/.xlsm`；
- 没有用户身份，谁改了计划、谁改了货损、谁删了历史，查不到；
- 客户公司如果两个人共用一台电脑，或开远程桌面给代运营，数据就是共享的。

**单人自用可以接受；一旦说是“给客户公司用”，这就是 P0。**

### 4.2 上传/内存/缓存：大文件会卡死

- 前端 `FileReader.readAsDataURL` 把 30 MB 文件转 base64，JSON body 上限约 41 MB；
- Python 端再 base64 decode、写临时文件、算 SHA、openpyxl 加载两份 workbook（formula + values）；
- `_cached_load(maxsize=6)` 最多缓存 6 个文件 × 2 份 workbook；30 MB 的 xlsx 展开后可能几百 MB，连续导几个文件就 OOM；
- `ThreadingHTTPServer` 同步分析，CPU/GIL 阻塞，大文件没有进度、没有取消、没有超时；
- 文档说“默认低负载”，实际是“闲时低负载，一分析就高负载”。

### 4.3 没有日志文件、没有本地数据导出/迁移、没有崩溃恢复

- 服务日志只 print 到终端；用户关掉终端，啥也没有；
- 历史 JSON 和 SQLite 只有一份，没有“导出全量数据”按钮；换电脑、换目录只能手动拷贝，配置和格式是否完整没有校验；
- 电脑坏了/磁盘满了属于用户自己的运维责任，工具不承诺电脑级容灾；但工具至少要保证本地数据可打包导出、可读、可迁移；
- 文档承诺“操作日志使用轻量本地文件”，当前没有实现。

### 4.4 SQLite / JSON 没有 schema 版本和迁移

- `daily.sqlite3` 没有 `schema_version`，以后加字段只能靠 `ALTER TABLE` 硬猜；
- 历史 JSON 没有 `schemaVersion`，桌面版/后续版本读旧快照可能崩；
- 没有 WAL、没有 `integrity_check`、没有 vacuum；本地数据整体导出/导入也未实现；
- 多开两个服务实例共享同一数据目录时，进程内锁不跨进程，SQLite 只能靠 20 秒 busy timeout 兜底。

### 4.5 配置在 localStorage，清个浏览器就没了

可复用配置只存浏览器 localStorage；换浏览器、换用户、清缓存、开无痕，全丢。历史快照里虽然带当次配置，但不能一键恢复成“我的常用配置”。客户会问：“我配了半天的映射呢？”

### 4.6 交付环境：Python、.command、签名、离线安装都没解决

- 需要 Python 3.10+ 和 openpyxl 3.1.5；
- 首次装依赖要联网；企业 Mac 可能没 Python、pip 被墙、代理不通；
- `.command` 双击在 macOS Gatekeeper 下可能被拦；Windows 还没有；
- 没有安装包、没有代码签名/公证、没有自动更新、没有回滚；
- “后续做 Mac/Windows 应用”是愿望，不是排期。

### 4.7 测试只证明了“代码按我写的逻辑跑”，没证明“客户数据能跑”

65 项自测里：

- 引擎 23 项、HTTP 15 项、历史 10 项、日记录 17 项；
- 没有真实仓库原表、没有真实多多导出、没有 7 天并行对账；
- 没有 fuzz、没有畸形 xlsx、没有 zip bomb、没有 100k 行、没有并发、没有崩溃恢复、没有本地数据导出/导入测试、没有多浏览器/多系统；
- 样例是整理过的 10 个商品、13 个工作表，且销量是 2025 年、其他明细是 2026 年——一个“日期都不一致”的样例，恰好能证明“工具会提示”，但不能证明“客户真实表能算对”。

## 5. 交付与商业：这不是一个能卖的产品，只是一个能演示的原型

1. **没有定价、没有 License、没有 EULA、没有 SLA。** 卖给谁、卖多少钱、含不含实施、出问题多久响应、本地数据导出/迁移谁负责，全没写。
2. **“客户确认后开源 GitHub”和“靠工具收费”逻辑打架。** 源码公开后，客户为什么付钱？买支持、买定制、买数据迁移？这些服务边界没定义。task.md 说已推送 `ljy-codes/retail-link`，项目规划又说“当前未创建或推送”，自己都没统一。
3. **没有本地数据导出/迁移机制。** 客户不用了，历史 JSON、SQLite、配置怎么打包带走？换电脑怎么迁？没有“导出全部数据/导入”按钮。电脑故障不是工具责任，但“数据可携带”是工具边界内的责任。
4. **没有支持体系。** 没有日志、没有版本兼容说明、没有远程诊断、没有升级回滚；一个人维护，客户环境千奇百怪，出事只能远程猜。
5. **平台读取侧的合规与失败恢复没评估。** 线上只读是明确需求，不写回平台；但拼多多有风控、验证码、子账号、平台协议，读取也可能触发限制。客户账号密码给本地脚本，出了事谁背？读取频率、失败重试、验证码/登录态过期、数据最小化都要写清楚。
6. **“单人本地”与“客户公司”矛盾。** 交接文档说单人，但客户公司通常有运营、仓库、采购、财务；没有权限和审计，没法多人用；强行多人用就是数据事故。
7. **“零售通”名字大于能力。** 现在只覆盖多多样例、单仓、单表、看盘；叫“零售通”会让客户期待多平台、多店、多角色、全链路，实际交付落差会反噬。
8. **长期大工程没有资源计划。** 没有人力、预算、里程碑、验收人、kill criteria；“长期大工程”四个字不是规划，是许愿。

## 6. 文档、测试与项目治理：最大的漏洞是“自己骗自己”

1. **65 项自测 ≠ 验收。** 自测通过只能说明“代码按设计跑”，不能说明“业务算对”。验收必须是：真实原表 + 人工结果 + 差异阈值 + 客户签字。
2. **5 个问题上限会掩盖风险。** 答疑文档只保留 5 项，但实际未确认的口径远不止 5 项（退款、平台费、活动、返利、批次、效期、多仓、多店、权限……）。没写进表里，不等于不存在，最后都会变成代码里的“默认假设”。
3. **文档互相打架。**
   - `task.md` 追加记录 38：已推送 GitHub `https://github.com/ljy-codes/retail-link`；
   - `项目规划.html`：当前尚未创建或推送 GitHub；
   - `使用说明.md`：未确认问题看 `概览/答疑文档/2026-11-21.md`，实际文件是 `零售通-20261121.xlsx`。
   客户读到三处不一致，第一反应不是“文档没更新”，而是“你的数能信吗？”
4. **优先级倒挂。** 外观做了浅/深/系统、两组配色、三档字号、16 项外观测试、40 次对比度检查；核心的“每日最低销量”一行没有。典型的“毛坯房先装水晶灯”。
5. **版本纪律弱。** v0.1.0 → v0.1.1 加了外观、玻璃、字号、每日价格，仍是 patch 版本；没有 CHANGELOG、没有迁移说明、没有“本版不兼容”提示。
6. **没有需求-测试-发布追溯。** 哪个需求对应哪个测试、哪个版本、哪个客户验收，查不到；全靠 task.md 流水账。
7. **“当前原型/本轮完善中/后续”与“已实现/已验证/已交付”混用。** 对外说“已交付”，对内说“原型”，客户和开发对同一版本的理解不一致。

## 7. 话术 vs 实际：几组“翻译”

| 对外话术 | 实际能力 | 翻译 |
| --- | --- | --- |
| 无需打开 Excel | 只支持 `.xlsx/.xlsm`；`.xls` 先另存；公式不重算；CSV 导出还会被 Excel 改格式 | “还是得开 Excel” |
| 主动识别问题 | 主要查行内金额 vs 数量×单价、编码冲突、日期年份；不查重复行、库存恒等式、退款、异常值 | “查了个寂寞” |
| 动态格式适配 | 别名匹配 + 人工映射；合并单元格、多级表头、无年份日期、多仓多表不保证 | “自适应 = 你自己配” |
| 历史可追溯 | JSON 快照 + 源文件 SHA；源文件移动/改名只能只读；没有整体导出/迁移 | “能看，但换电脑/换目录麻烦” |
| 低负载运行 | 无操作不轮询；一分析就两份 workbook、base64、同步阻塞 | “闲时低负载，忙时高负载” |
| 单人本地使用 | 无登录、无权限、无审计；共享电脑即共享全部数据 | “单人 = 一个人背锅” |
| 本地完全离线 | 首次装依赖要联网；Python 环境/签名/安装包没有 | “离线个寂寞” |
| 客户确认后开源 | 文档对“是否已推送”自相矛盾；开源后商业模式未定 | “先开源，再想怎么收钱” |

## 8. 真实场景压力测试：10 个必翻车现场

1. **商品列合并单元格**：只有第一行有商品名，下面行全跳过 → 销量少一半。
2. **表头写“11.20”没有年份**：历史文件按当前年份套 → 2025 年数据算成 2026 年。
3. **数量写“10箱”**：`_number` 失败 → 行被丢，提示“数量无效”。
4. **同一商品两行（南京仓/芜湖仓）**：直接相加，没有仓库维度 → 库存虚高或重复。
5. **昨天真没卖、单元格空着**：日均销量算不出，可售天数 `—`。
6. **后台销量含退款/仅退款**：销量虚高，补货建议偏乐观。
7. **商品简称改了一个字**：历史两套商品，趋势断。
8. **三个出库 sheet**：只读第一个，另外两个仓当没看见。
9. **18 位商品 ID 以数字存**：float 精度丢位，两个 ID 可能撞车。
10. **导出 CSV 给财务**：`00123` 变 `123`，长 ID 变 `3.02E+11`，对账对不上。

## 9. 如果我是甲方，验收会问这 15 个问题

1. 退款、退货、仅退款算不算销量？你这张表的“销量”到底是哪个口径？
2. 南京仓和南京多多是不是同一个库存池？可售天数按哪个算？
3. 85% 是金额还是件数？按单品、品牌还是全店？完不成返利扣多少？
4. 商品 F 销量 0、金额 4432，你保留源金额，达成率还算不算？
5. 货损 2 个、单价 7.7、金额填 77，你的货损率依据是什么？
6. 秒杀坑位费 5000、卖 200 单，亏不亏？表里哪一列能看出来？
7. 活动价 9.9、成本 12，系统会不会拦？总部最低价在哪校验？
8. 三个仓、两个店、一天一个导出，你怎么合并？会不会漏仓？
9. 仓库表写“10箱”，你为什么识别不了？还要我回去改成数字？
10. 11.20 的表头没有年份，你识别成 2025 还是 2026？
11. 同一张表复制两行，销量翻倍，你的“主动发现问题”为什么没提示？
12. 导出 CSV 给财务，前导零和长 ID 怎么办？
13. 两个运营同时用，谁改了计划？日志在哪？能不能回滚？
14. 本地数据能不能整体导出？换电脑能不能迁移？电脑故障/网盘备份是用户责任，不作为工具验收项。
15. 客户电脑没 Python、没网、Gatekeeper 拦截，你怎么交付？

## 10. 最小补救路线（建议，不是加功能）

### 第 0—2 周：先别写新功能，先把“能不能算对”解决

1. **冻结口径**：把答疑文档从 5 项扩到“全量未确认清单”，逐项写：默认值、影响指标、确认人、确认日期。没有确认的，页面必须显示“假设”标签。
2. **拿真实样本**：仓库原始登记/盘点表、多多后台原始销量导出、连续两天售价表、一份到货单。没有这些，不再宣称“格式自适应”。
3. **做 7 天并行对账**：人工算 vs 工具算，按商品、按指标列差异；定义阈值（建议金额 ±0.5%、数量 0、比率 ±0.1 个百分点）。达不到，不叫 v0.2。
4. **补数据地基**：稳定 SKU 主键、单位字段、去重键、真实零录入、合并单元格填充、18 位 ID 文本化。

### 第 2—6 周：把“看盘”变成“操盘”

1. 退款/退货/仅退款口径，净销量与成交额。
2. 货损恒等式：期初 + 入库 - 出库 - 实盘 = 货损，差异可追溯。
3. 每日最低销量、建议报单量、补货点/补货量、活动价风险。
4. 日价格/销量接入主看盘：价格趋势 + 销量趋势 + 活动日历。
5. Excel 导出（多 sheet、格式、编码文本化）、本地数据整体导出/导入（备份位置由用户决定）。
6. 多仓/多店/多文件合并，至少支持“选择多个文件 + 合并规则 + 冲突提示”。

### 第 6—12 周：再谈自动化和桌面端

1. 告警（微信/钉钉/邮件/本地通知）、定时扫描、失败重试。
2. 共享电脑的登录/令牌、操作审计、权限（至少“查看/修改/删除”三级）。
3. 日志文件、崩溃恢复、SQLite WAL/schema 迁移、安装包/签名/自动更新。
4. 商业条款：定价、License、SLA、开源边界、数据迁移与退出。

### 现在就应该停止的事

- 停止在核心口径未确认前继续做主题、玻璃、字号、配色；
- 停止用“65 项自测”对外说“已验证”；
- 停止把“后续能力”写进当前版本的价值主张；
- 停止用“样例能跑”证明“客户能跑”。

### 这一版的“完成”定义

> 连续 7 天真实数据，工具结果与人工结果逐商品对账，关键指标差异在约定阈值内；所有异常 100% 可解释、可定位、可还原；客户业务负责人签字确认口径。做不到，就还是原型。
