## 3. 问题清单（按优先级）

### P0-1 净销量未实现，当前仍是“映射销量”

- 依据：11/22 答疑 E5 选 **C（净销量：发货量扣退款、退货、取消）**；`阶段性总结` 顶部和 `项目规划` 都写明“尚未自动重建净销量”。
- 代码现状：`analyzer.py` 的 `sales` 角色只有数量/金额，没有退款、退货、取消、订单状态、明细 ID；`role_data["sales"]` 直接汇总映射销量。
- 影响：日均销量、可售天数、补货建议、活动节奏全部基于毛销量；拼多多退款/仅退款比例一高，结果会偏乐观。
- 验收判定：**不通过**。在净销量落地前，界面应明确写“映射销量，不是净销量”，不能只写“平台销量”。

### P0-2 货损双轨未实现，当前只读登记值

- 依据：11/22 答疑 E7 选 **C（登记值与公式重建并列核对）**；公式背景为期初 + 入库 − 出库 − 实盘。
- 代码现状：只读 `lossAmount` / `lossQuantity`，用 `lossAmount / outboundAmount` 算货损率；没有期初、入库、实盘核对，也没有“登记值 vs 重建值”的差异表。
- 影响：货损率可能只是仓库手填值；样例商品 B 的 2 个 × 7.7 与手填 77 仍只能提示“不一致”，不能给出双轨结论。
- 验收判定：**不通过**。至少应把“登记货损”“公式重建货损”“差异/待确认”分列。

### P0-3 真实业务验收未开始

- `概览/答疑文档/零售通-20261123.xlsx` 新增 3 项，解答列均为空：
  1. 发货/售后样本：A/B/C 未答；
  2. 跨期售后归属：A/B/C 未答；
  3. 首批试用范围：A/B/C 未答。
- 现有 `原始资料/订货数据`、`价格记录` 只能做格式适配，不能替代发货/售后明细。
- 因此：没有真实净销量对账、没有 7 天连续试用、没有客户人工结果对照、没有签字。
- 验收判定：**未开始**。技术测试通过不等于业务验收通过。

### P1-1 源文件写回未实现

- 依据：11/22 答疑 E8 选 **C（默认新建，设置中开启写回，每次预览确认）**。
- 代码现状：原件仍只读；`产品交付` 使用说明也写“用户原始 Excel 保持只读”；没有写回开关、差异预览、备份、原子写、重读校验。
- 影响：已确认的“本地读写”只兑现了“读 + 导出新文件”，没有兑现“受控写回源文件”。
- 验收判定：**未交付**（但方向已确认，文档披露充分）。

### P1-2 多仓库存被合并，产品行只显示一个仓库

- 依据：11/21 已确认“按地区分仓、存在多仓、库存不等于平台销量、可能退回自有仓”。
- 代码现状：`dataset_service` 能按商品+仓库校验库存快照，但 `analyzer.py` 最终 `meta` 以商品为 key，库存 `stockSmall/stockLarge/stockAmount` 跨仓相加，`warehouse` 只保留第一次出现的仓库。
- 复现：同一商品南京仓 100、芜湖仓 200，分析后为 `warehouse=南京仓`、`stockSmall=300`、`stockAmount=3000`，没有“南京仓 100 / 芜湖仓 200”的分仓视图，也没有跨仓提示。
- 影响：分仓可售天数、平台退回自有仓、补货判断和库存池核对都会被合并值掩盖。
- 验收判定：**不通过（多仓口径）**。需要“商品 × 仓库”维度，至少展示分仓库存与分仓可售天数；合计值只能作为辅助。

### P1-3 合计达成率在“非正计划/未知商品”时会出现无效值

- 依据：单品考核要求“未知输入单列待核对”，但汇总仍计算 `achievement = 合计完成 ÷ 合计计划`。
- 复现：商品 A 计划 0、完成 200；商品 B 计划 100、完成 100。结果：
  - `unknownTargetCount = 1`，`targetGap = null`（正确）；
  - 但 `summary.plan = 100`、`summary.completed = 300`、`summary.achievement = 3.0`（300%）。
- 影响：UI 顶部“合计计划达成率”会显示 300%，即使旁边写了“合计展示，非单品结论”，也会误导老板/运营。
- 建议：只要存在 `plan <= 0` 或 `plan is None` 或 `completed is None`，`summary.achievement` 应为 `null`（或明确“不可计算”），并单独展示“已知商品合计”。当前只对 `None` 做了空值保护，未覆盖非正计划。

### P1-4 交付 HTML 对“未实现口径”披露不够具体

- `README` 和 `阶段性总结` 已披露净销量、货损双轨、源写回未实现；
- 但 `产品交付/零售通-v0.1.7-使用说明.html` 只在页脚写“业务口径与真实原表对账仍需持续验证”，没有明确写：
  - 当前销量是映射销量，不是净销量；
  - 当前货损是登记值，不是双轨核对；
  - 当前原件只读，源写回尚未实现。
- 影响：试用客户会按“已确认口径”理解结果，容易把毛销量当净销量、把登记货损当核算结果。
- 建议：在 HTML 的“开始看盘/数据说明”处加三条显著提示，与版本能力一致。

### P1-5 正式分发条件未满足

- 当前 `spctl -a -vv` 结果为 `rejected`，签名是 ad-hoc，`TeamIdentifier=not set`，未做 Developer ID 公证。
- 仅 x86_64，Apple Silicon 原生包未验证；Windows v0.1.8 无安装包；安装/升级/普通卸载/彻底卸载未在可丢弃测试机走完整矩阵；exFAT/FAT 移动盘硬链接兼容未实现。
- 影响：本机/试用可运行，客户下载后可能被 Gatekeeper 拦截；不能作为正式对外分发版本。
- 验收判定：**有条件通过（仅 Intel Mac 本机试用）**。

### P2-1 顶部 KPI 仍以“合计达成率”为第一视觉

- 页面顶部第一 KPI 是“合计计划达成率”，后面才出现“单品目标考核”卡片；虽然文字标注“合计展示，非单品结论”，但单品考核是当前真正的决策口径。

### P2-2 测试脚本会把字节码写进 App 包

- 这是测试环境问题，不是 App 运行时缺陷（`Main.swift` 已设置 `PYTHONDONTWRITEBYTECODE=1`）。

### P2-3 11/23 答疑文档尚未进入 task 记录

- `概览/答疑文档/零售通-20261123.xlsx` 已存在（3 项未答 + 已确认结论页），但 `task.md` 最后记录仍是追加记录 53，未登记本轮答疑；
- 影响：当前进度/问题清单与最新答疑文件不同步，后续容易重复问或漏答。
- 建议：补一条 task 记录，明确 11/23 问卷是“未答/待资料”，不要把推荐项当成用户确认。

### P2-4 样例严格日期下销量为空、10 款全部未达标

## 5. 建议的下一步顺序

1. **先做净销量结构，不先做自动化**：按已确认 C，引入发货/售后明细 ID、状态、业务日期和跨期归属；缺字段时明确显示“映射销量”，不冒充净销量。
2. **再做货损双轨**：登记值、期初+入库−出库−实盘重建值、差异/待确认三列并列；缺期初/入库/出库/实盘时保留未计算。
3. **补多仓维度**：商品 × 仓库为主键的库存与可售天数；合计只做辅助，避免跨仓掩盖。
4. **修汇总达成率边界**：存在非正计划/未知商品时，合计达成率置空或标注“不可计算”；不要把 300% 这种值显示给业务。
5. **补源写回**：默认新建，设置中开启写回，逐次预览、备份、原子写、重读校验、可回滚。
6. **真实业务验收**：拿到 11/23 三项资料后，用连续 7 天真实数据做人工 vs 工具并行对账；差异阈值和客户签字先定。
7. **分发条件**：Developer ID 公证、Apple Silicon、Windows、安装/卸载矩阵、exFAT/FAT 兼容；未完成前只按“Intel Mac 本机试用包”表述。
8. **测试卫生**：README/脚本统一 `PYTHONPYCACHEPREFIX`，避免把测试字节码写进 App 包；App 包测试后再校验一次“无 `__pycache__`/`.pyc`”。
