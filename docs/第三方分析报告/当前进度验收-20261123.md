# 零售通 v0.1.9 · 当前进度验收报告

> 验收日期：2026-11-23（Asia/Shanghai）  
> 验收对象：Mac v0.1.9（Windows 配对计划 v0.1.10，功能基线 desktop-3）、产品交付 DMG/HTML、GitHub main/macos/windows、概览与答疑记录  
> 验收方式：读代码与文档 + 复跑测试 + DMG 只读挂载与签名检查 + 合成边界用例 + 真实原表只读结构核对 + 与 11/22 已确认口径逐条对照

## 4. 问题清单（按优先级）

### P0-1 净销量仍未实现，当前看盘仍是“映射销量”

- 依据：11/22 答疑 E5 选 **C（净销量：发货量扣退款、退货、取消）**；`阶段性总结`/`项目规划`/`README` 均写明尚未自动重建。
- 代码现状：`analyzer.py` 的 `sales` 角色没有退款、退货、取消、订单状态、明细 ID；日记录也明确“销量沿用来源当日销量，未自动扣除售后”。
- 影响：日均销量、可售天数、补货建议、活动节奏仍可能偏乐观；拼多多退款/仅退款比例一高，误差会放大。
- 验收判定：**不通过**。当前页面/导出应继续明确“映射销量，不是净销量”；不能只写“平台销量”。

### P0-2 货损双轨仍未实现，当前只读登记值

- 依据：11/22 答疑 E7 选 **C（登记值与公式重建并列核对）**；公式背景为期初 + 入库 − 出库 − 实盘。
- 代码现状：只读 `lossAmount` / `lossQuantity`，用 `lossAmount / outboundAmount` 算货损率；没有期初、入库、实盘核对，也没有“登记值 vs 重建值”差异表。
- 影响：货损率仍可能只是仓库手填值；样例商品 B 的 2 个 × 7.7 与手填 77 只能提示“不一致”，不能给出双轨结论。
- 验收判定：**不通过**。至少应把“登记货损”“公式重建货损”“差异/待确认”分列。

### P0-3 真实业务验收未开始

- `概览/答疑文档/零售通-20261123.xlsx` 3 项解答仍为空：
  1. 发货/售后样本；
  2. 跨期售后归属；
  3. 首批试用范围。
- 真实价格表只有 13 个日期组、169 个全空价量组合，只能做结构适配，不能做数值对账。
- 因此：没有真实净销量对账、没有连续 7 天人工结果对照、没有客户签字。
- 验收判定：**未开始**。221 项技术测试通过不等于真实业务验收通过。

### P1-1 源文件写回仍未实现

- 依据：11/22 答疑 E8 选 **C（默认新建，设置中开启写回，每次预览确认）**。
- 代码现状：v0.1.9 原件仍只读；`产品交付` 使用说明也写“用户原始 Excel 保持只读”；没有写回开关、差异预览、备份、原子写、重读校验。
- 影响：已确认的“本地读写”只兑现“读 + 导出新文件”，没有兑现“受控写回源文件”。
- 验收判定：**未交付**（方向已确认，HTML 已披露）。

### P1-2 多仓库存仍被合并，产品行只显示一个仓库

- 依据：11/21 已确认“按地区分仓、存在多仓、库存不等于平台销量、可能退回自有仓”。
- 代码现状：`dataset_service` 能按商品+仓库校验库存快照，但 `analyzer.py` 最终 `meta` 以商品为 key，`stockSmall/stockLarge/stockAmount` 跨仓相加，`warehouse` 只保留第一次出现的仓库。
- 复现（v0.1.9 实测）：同一商品南京仓 100、芜湖仓 200，分析后 `warehouse=南京仓`、`stockSmall=300`、`stockAmount=3000`，没有“南京仓 100 / 芜湖仓 200”分仓视图，也没有跨仓提示。
- 影响：分仓可售天数、平台退回自有仓、补货判断和库存池核对都会被合并值掩盖。
- 验收判定：**不通过（多仓口径）**。需要商品 × 仓库维度；合计只应作为辅助。

### P1-3 合计达成率在“非正计划/未知商品”时仍会产生无效值

- 依据：单品考核要求“未知输入单列待核对”，但汇总仍计算 `achievement = 合计完成 ÷ 合计计划`。
- 复现（v0.1.9 实测）：商品 A 计划 0、完成 200；商品 B 计划 100、完成 100。结果 `unknownTargetCount=1`、`targetGap=null` 正确，但 `summary.plan=100`、`summary.completed=300`、`summary.achievement=3.0`（300%）。
- 影响：顶部“合计计划达成率”会显示 300%，即使旁边写“合计展示，非单品结论”，也会误导老板/运营。
- 建议：只要存在 `plan <= 0` 或 `plan is None` 或 `completed is None`，`summary.achievement` 应为 `null`（或明确“不可计算”），并单独展示“已知商品合计”。当前只对 `None` 做了空值保护，未覆盖非正计划。

### P1-4 商品关联只用于日记录，主看盘仍未使用同一对照

- 依据：本轮商品关联保存在 `daily.sqlite3`，用于日记录导入；`README` 明确“当前用于日记录导入，不追溯改写既有记录”。
- 代码现状：`analyzer.py` 仍按导入表里的商品标识合并；`product_catalog` 不参与主看盘的商品关联。
- 影响：日记录里同一个标准商品可能对应多个来源 ID，但主看盘的销量/库存仍按原始 ID 分开，跨来源核对时会对不上。
- 建议：把商品关联作为主分析与日记录共用的“商品主数据”输入；至少在主看盘显示“来源 ID → 标准商品”映射和未关联项。

### P1-5 真实订货表存在“同一商品 ID 不同规格”，当前商品关联会整组排除

- 真实 `原始资料/订货数据/零售通-订货管理-20261121.xlsx` 实测：商品 ID `示例商品ID（公开副本已脱敏）` 同时对应 `A / 1件` 与 `B / 1组`；`parse_catalog` 正确拒绝自动合并，但把该 ID 整组暂不导入，最终 7 条有效、1 条待处理。
- 影响：真实商品关联会少 2 款；如果用户只看到“1 条问题”，容易忽略这两个商品。
- 建议：商品关联 key 至少加入规格/SKU，或提供“同一来源 ID 拆分为多个标准商品”的人工流程；不能只靠来源 ID + 仓位。

### P1-6 正式分发条件仍未满足

- `spctl -a -vv` 结果 `rejected`；ad-hoc 签名、`TeamIdentifier=not set`，未做 Developer ID 公证。
- 仅 x86_64；Apple Silicon 原生包未验证；Windows v0.1.10 无安装包；安装/升级/普通卸载/彻底卸载未在可丢弃测试机走完整矩阵；exFAT/FAT 移动盘硬链接兼容未实现。
- 影响：本机/试用可运行，客户下载后可能被 Gatekeeper 拦截；不能作为正式对外分发版本。
- 验收判定：**有条件通过（仅 Intel Mac 本机试用）**。

### P2-1 顶部 KPI 仍以“合计达成率”为第一视觉

- 页面顶部第一 KPI 仍是“合计计划达成率”，单品目标考核卡片在下面；虽然文字标注“合计展示，非单品结论”，但单品考核才是当前决策口径。
- 建议：把“未达标款数”或“最低单品达成率”提升为第一 KPI，合计达成率降为辅助；或在合计 KPI 上叠加“1 款未达标”红色角标。

### P2-2 真实价量表格式适配仍偏窄

- 当前 `detect_paired_mapping` 主要识别相邻的“销量/售价”或“当日销量/当日售价”列；真实表刚好匹配。
- 如果实际表使用“销量(件)/售价(元)”“销售额/退款”等表头，自动识别可能失败，需要人工配置或后续适配。
- 本轮真实价格表 169 个价量组全空，无法证明“有值时”的完整业务链路。

### P2-3 商品关联使用“仓库名称”而不是“仓库 ID”

- 真实订货表同时有 `仓库ID` 和 `仓库名称`；`parse_catalog` 取 `仓库名称` 作为 `sourceShop`。
- 如果两个仓库同名、名称变更或跨地区复用，来源键可能冲突或断链；建议把来源仓库 ID 纳入 key，名称只做显示。

### P2-4 CSV 导出仍存在 Excel 二次解析风险

- Excel 导出已把商品 ID/文本列设为文本；CSV 只做公式前缀转义，前导零/长数字仍可能被 Excel 二次转换。
- 对财务或需要二次编辑的场景，优先 Excel；CSV 需在说明中标注“仅用于交换，不保证 Excel 打开后的类型”。

### P2-5 文档有小幅漂移

- `阶段性总结` 顶部“当前有效业务结论”表仍写“Mac v0.1.7已实现逐款状态”，当前版本已是 v0.1.9；功能覆盖不变，但版本引用滞后。
- 建议：统一改成“Mac v0.1.7 起实现，v0.1.9 继续包含”，避免读者误以为当前仍是 v0.1.7。

### P2-6 测试/构建卫生

- `开发空间/desktop/build` 已按整理记录清理；仓库不存构建产物，复跑现成 App 测试需要先从 DMG 恢复或重新构建。
- 若直接用 App 内置 Python 跑测试且不设 `PYTHONPYCACHEPREFIX`，可能在 App 包内生成 `__pycache__`，触发“资源只读/无测试数据”检查失败。
- 建议：README/测试脚本统一 `PYTHONPYCACHEPREFIX`，并明确“先用 DMG 或重建 App”再跑现成 App 专项测试。

## 6. 建议的下一步顺序

1. **净销量结构先行**：引入发货/售后明细 ID、状态、业务日期和跨期归属；缺字段时明确写“映射销量”，不冒充净销量。
2. **货损双轨**：登记值、期初+入库−出库−实盘重建值、差异/待确认三列并列；缺数据保留未计算。
3. **多仓维度**：商品 × 仓库为主键的库存与可售天数；合计只做辅助。
4. **修汇总达成率边界**：存在非正计划/未知商品时，合计达成率置空或标“不可计算”。
5. **商品关联升级为主数据**：主看盘与日记录共用；key 加入规格/SKU，解决真实订货表“同一 ID 多规格”问题。
6. **源写回**：默认新建，设置中开启写回，逐次预览、备份、原子写、重读校验、可回滚。
7. **真实业务验收**：拿到 11/23 三项资料后，用连续 7 天真实数据做人工 vs 工具并行对账；差异阈值和客户签字先定。
8. **分发条件**：Developer ID 公证、Apple Silicon、Windows、安装/卸载矩阵、exFAT/FAT 兼容；未完成前只按“Intel Mac 本机试用包”表述。
9. **测试卫生**：README/脚本统一 `PYTHONPYCACHEPREFIX`，并明确先恢复/重建 App；测试后校验 App 包无 `__pycache__`/`.pyc`。
