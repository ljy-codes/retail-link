# 零售通 GitHub 分支与版本规定

更新：2026-11-26。长期只保留 `main`、`macos`、`windows` 三条分支，默认分支为 `main`。

2026-11-26 最新用户准则：**macOS 与 Windows 功能必须一致，应用 Logo / 图标必须一致；实现方式按各自系统选择。Windows 开发不得修改 `macos` 分支或代写 macOS 实现，macOS 开发不得修改 `windows` 分支或代写 Windows 实现。跨端修改必须得到用户明确授权。** 本节现行准则优先于下文历史记录中的开发顺序与同步安排。

| 分支 | 用途 |
| --- | --- |
| main | 完整工程的共享基线：server、backend、web、跨平台功能清单、通用测试、概览与答疑。共享业务规则只维护一份。 |
| macos | 基于main的完整工程，维护Mac系统交互、应用与DMG构建、签名、Mac验证及发布记录。 |
| windows | 基于main的完整工程，维护Windows系统交互、安装卸载、Windows验证及发布记录。已发布技术版本为Windows v0.2.6，本地待人工安装候选为v0.2.8。 |

## 开发顺序

macOS 或 Windows 均可先行开发。共享功能定义、业务规则、功能清单、图标设计源和验收口径以 `main` 为准，共享改动进入 `main` 后，由各平台负责人自行同步到自己的平台分支并完成适配和验证。平台分支保留完整工程；平台差异限定为系统接口、路径、容器、打包、签名与交付脚本，不能各自维护不同的库存、销量、计划或货损算法。

### 功能与图标一致性

- 两端面向用户的功能、业务口径、输入输出和功能入口必须保持一致。允许使用各自系统的原生窗口、文件选择器、系统接口和构建方式；实现技术不要求相同。
- 两端使用同一份经用户确认的 Logo / 图标设计源，主体图形、配色和品牌含义一致。可以分别生成 Windows ICO、macOS ICNS 等所需格式、尺寸和系统容器适配，不能自行换成另一套图形或配色。
- 图标候选尚未选定时不得当作正式图标替换发布。选定后由两个平台分别接入同一设计源。
- 一端先完成的暂时差异必须在 `main` 的配对版本 / 待适配记录中列明功能、图标状态、目标版本、负责平台和待验收项；另一端未实现或未实测时，必须明确标记待适配或待验收，不能宣称两端已经一致。
- 发布 / 验收时逐项对照同一功能清单和图标源，分别保留两端验证结果；一端测试通过不能替代另一端实机验证。

### 分支归属与跨端修改边界

| 执行环境 / 开发方 | 默认可维护范围 | 禁止范围 |
| --- | --- | --- |
| Windows | `main` 中共享定义、共享代码及文档；`windows` 分支和 Windows 平台实现。 | 修改、合并、推送、重置或删除 `macos` 分支；编写 / 修改 macOS 平台实现代码，即使该代码位于 `main`。 |
| macOS | `main` 中共享定义、共享代码及文档；`macos` 分支和 macOS 平台实现。 | 修改、合并、推送、重置或删除 `windows` 分支；编写 / 修改 Windows 平台实现代码，即使该代码位于 `main`。 |

只读查看对方代码、对照功能和记录差异可以进行。不能通过自动同步脚本、CI、代理或合并操作绕过分支归属；“保证两端一致”“正常推送 GitHub”不自动构成跨端修改授权。

仅当用户明确要求“macOS 可以修改 Windows”或“Windows 可以修改 macOS”时，才允许在本次任务的授权范围内操作。应在提交 / 变更记录中保留授权内容及影响范围；没有明确授权时，差异交由对方平台实现。

### 任一端先行与版本预留

- macOS 先完成或 Windows 先完成均可为另一端预留配对版本号；预留记录写入 `main` 的版本 / 发布记录，并标注“预留 / 待实现 / 待验收”。
- 预留版本只表达目标，不授予修改对方分支、对方平台代码或代做对方实现的权限。不为了预留编号而修改对方分支的 `版本.json`、构建配置、图标资源或发布标签。
- 记录应包含先行平台与已完成范围、另一端目标版本、共享功能基线、待适配功能 / 图标、负责平台及验收状态。沿用下方奇偶编号规则，分配前核对现有版本和标签，避免重号。
- 另一端自行认领预留版本，完成实现和平台验收后再更新实际状态。版本预留、源码同步、生成安装包和正式发布分别记录。

仓库根 `版本.json` 仅记录所在分支的源码状态：main不固定运行平台，由宿主自动识别；平台分支分别保留Mac/Windows版本及待验收状态。实际App载荷的版本与平台信息由各构建入口根据 `desktop/release.json` 生成，不能用源码同步替代安装包验收。

发布前同步main，使用同一功能清单与虚构样本对照结果，核对desktop/验收清单.md。临时feature/fix/codex分支完成合并或交付后清理，旧版通过提交历史追溯，不另建长期版本分支。

## 本项目版本规则

- 采用X.Y.Z；Mac的Z为奇数，Windows的Z为大于配对Mac补丁号的偶数。历史已发布Mac0.2.1、Windows0.2.6，本地待人工安装候选Windows0.2.8，功能基线desktop-4。
- 标签必须带平台后缀：`v<X.Y.Z>-macos`、`v<X.Y.Z>-windows`。
- Mac v0.2.1构建源码标签使用`v0.2.1-macos`，锚定已验收提交`fbb54cf`；随后合并远端Windows工程与兼容改动并同步三个分支。新标签远端核对后按规则清理旧Mac标签，历史源码继续从Git提交历史追溯，不重写历史提交。
- Windows v0.2.4构建源码标签使用`v0.2.4-windows`，对应GitHub Release保留安装包与Windows说明两个资产；已经发布的`v0.2.2-windows`保留，不覆盖或复用。
- Windows v0.2.6构建源码标签使用`v0.2.6-windows`，对应GitHub Release保留安装包与Windows说明两个资产；已经发布的`v0.2.4-windows`和`v0.2.2-windows`保留，不覆盖或复用。
- 后续Windows-only维护版本从0.2.6按2递增为0.2.8、0.3.0等，始终大于当前配对Mac补丁号；只有生成并验收新的Mac功能基线时才同步提升Mac奇数版本。
- 每个平台长期只保留最新交付标签和下载入口；删除旧入口前先确认新版完整。历史源码始终从Git提交记录追溯，不重写历史提交。

## 交付与同步

客户本地“产品交付”只保留最新安装包和对应HTML说明两文件。App、DMG、运行环境二进制、业务原表、运行数据、凭据及测试产物不提交到源码树。用户答疑和概览按既有授权及时同步；答疑已确认不等于功能已实现。

历史Windows0.2.6发布经用户明确授权推送源码、文档及纯虚构测试，更新`windows`分支和`v0.2.6-windows`标签，并发布与标签对应的两个Release资产。该历史授权不扩展为本次0.2.8候选的Release授权。发布说明标明配对Mac版本、共享源码、构建环境、验证范围与限制；技术验收、客户验收和完整业务验收分别表述，未完成项不得写成已通过。

规则参考：https://github.com/ljy-codes/api-workbench/blob/main/docs/platform-branch-and-version-policy.md 。本项目的Mac奇数／Windows偶数和“两文件交付”沿用用户已确定的约定；平台职责与跨端授权以本文最新用户准则为准。
